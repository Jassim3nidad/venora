# Database

Venora uses Supabase PostgreSQL in the `public` schema plus Supabase-managed
`auth` and `storage` schemas. At this baseline, 71 SQL files build the schema;
the API inventory documents 94 callable database functions. Migration history,
not generated TypeScript, is authoritative.

## Main domains

| Domain          | Representative data and behavior                                                           |
| --------------- | ------------------------------------------------------------------------------------------ |
| Identity/access | profiles, user roles, organizations/members, partner applications, admin roles/permissions |
| Venues          | venues, categories, images, packages, amenities, availability/calendar                     |
| Bookings        | inquiries/bookings, messages, status/cancellation history, snapshots, overlap guards       |
| Suppliers       | profiles/services, favorites, inquiry snapshots, quotes, messages, availability            |
| Payments        | attempts/sessions/events, refunds, receipts, invoices, commissions and snapshots           |
| Notifications   | notifications, preferences, subscriptions, delivery records and retries                    |
| Reviews         | review workflow, moderation, photos, responses, eligibility                                |
| Analytics/admin | reporting views/RPCs, marketplace monitoring, audit logs, settings                         |
| AI              | search embeddings, configurations, comparison/generated content, usage logs                |

Important enums include application roles, account/partner states, booking
statuses, notification channels/statuses, payment/refund states, and review
workflow states. Read the defining migration before extending an enum because
PostgreSQL enum changes and deployed ordering have rollback constraints.

## Relationships and integrity

Profiles link to Supabase Auth identities. Organizations and ownership scope
venue management. Bookings reference customer/venue/package while storing price
and event snapshots. Payment records reconcile to a booking and provider event.
Supplier inquiry snapshots expose only the event context intended for eligible
suppliers. Reviews require booking eligibility. Foreign keys, unique indexes,
checks, triggers, and transactional RPCs enforce important invariants.

Booking-integrity functions guard availability, capacity, active-date overlap,
approval, checkout races, confirmation, cancellation, and notification history.
Payment reconciliation validates provider reference, amount, currency, event
claim, settlement, commission snapshot, receipt/invoice, and audit effects.

## RLS, functions, and audit

RLS is expected on application tables, but deployed policy/grant state was not
queried. Policies scope rows by identity, role, organization, ownership,
eligibility, or admin permission. Storage uses separate policies. Security-
definer functions must set safe search paths, validate caller/resource access,
and expose execute only to intended roles.

Triggers and helper functions create status history, notifications, timestamps,
and audit evidence. Admin/payment operations that bypass ordinary user RLS need
explicit authorization and audit logging.

The complete code-backed RPC inventory is
[Supabase RPC functions](api/supabase-rpc.md). Storage policy details are in
[Storage](storage.md).

## Generated types and current risk

`packages/database/types/generated.ts` is generated by `pnpm db:types`. It
includes the migration `070` supplier portfolio fields but still does not appear
to include several other later domains (admin access, partner applications,
supplier quotes, settings, and AI configuration), so treat it as **CURRENT BUT
INCOMPLETE**. Do not hand-edit it. First repair/rehearse the duplicate `068`
migration history in an isolated environment, apply every migration, regenerate,
review the diff, type-check, and test.

See [Migrations](migrations.md) for safe local/hosted procedures.
