# User flows

Flow status reflects implemented source, not production acceptance. See
[authentication](../api/authentication.md), [Server Actions](../api/server-actions.md),
and [payment webhooks](../api/webhooks.md) for authoritative contracts.

## 1. Visitor browses venues — PARTIALLY IMPLEMENTED

- **Actor / start / preconditions:** Anonymous visitor at `/`; no session required.
- **Entry and steps:** Public navigation → `/venues` → filters/cards → `/venues/[slug]`.
- **Integration / status:** Public venue queries and `loadMoreVenuesAction`; browsing
  does not change state. No notification.
- **Outcome / recovery / permission:** Detail is success; empty/filter reset or retry
  is recovery. Confirmed load-more count defect and card identity risk remain.

```mermaid
flowchart TD
  A["Landing or public navigation"] --> B["Open venue marketplace"]
  B --> C["Search, filter, or scan cards"]
  C --> D{"Matching venue?"}
  D -->|Yes| E["Open venue detail"]
  D -->|No| F["Empty result; clear filters"]
  B --> G{"Load more offered?"}
  G -->|Yes| H["Request next page"]
  H --> C
```

## 2. Visitor registers as a customer — IMPLEMENTED BUT NOT RUNTIME-VERIFIED

- **Actor / start / preconditions:** Visitor at `/register`; valid email and strong
  password, no active account assumed.
- **Steps / status:** `registerAction` validates and calls Supabase sign-up;
  `new → verification pending`. Verification email is generated by Supabase.
- **Outcome / recovery / permission:** Generic success avoids account disclosure;
  validation/provider errors remain on form. Public action; resend is available.

```mermaid
flowchart TD
  A["Open registration"] --> B["Enter name, email, and password"]
  B --> C{"Client and server validation pass?"}
  C -->|No| D["Show correctable field errors"]
  D --> B
  C -->|Yes| E["registerAction"]
  E --> F["Create account and send verification email"]
  F --> G["Show verification-pending guidance"]
```

## 3. Existing verified user registers again — IMPLEMENTED BUT NOT RUNTIME-VERIFIED

- **Actor / start / preconditions:** Existing verified user submits the same email
  at `/register` while signed out.
- **Steps / decision:** `registerAction` delegates account handling to Supabase and
  returns generic feedback rather than confirming account existence.
- **Outcome / recovery / permission:** User proceeds to `/login` or password reset.
  No role permission applies; provider-specific mail behavior was not run.

```mermaid

  C --> D{"User remembers password?"}
```

## 15. Webhook settles and confirms booking — IMPLEMENTED; NOT BROWSER-VERIFIED

- **Actor / start / preconditions:** PayMongo server posts a signed event with a
  correlatable transaction, amount, currency, booking, and payment kind.
- **Steps / transition:** `POST /api/webhooks/paymongo` verifies signature, claims
  event, and calls `confirm_booking_payment`; `payment pending → paid` and
  `booking approved → confirmed`.
- **Outcome / recovery / permission:** Receipt, audit, history, commission, and
  notifications are created. Duplicate is safe; failure returns retryable 500.

```mermaid
flowchart TD
  A["Receive PayMongo event"] --> B{"Signature and age valid?"}
  B -->|No| C["Reject without mutation"]
  B -->|Yes| D{"Event claim new?"}
  D -->|No| E["Return duplicate success"]
```
